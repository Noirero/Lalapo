============================================================
0A. CORE RULES
============================================================

1. Pahami task dan intent owner.
2. Verifikasi required input material benar-benar tersedia dan dapat dibaca.
3. Gunakan repository aktual sebagai evidence kondisi implementasi saat ini.
4. Gunakan governing document/task authoritative untuk intended behavior/policy.
5. Investigasi root cause/design path sebelum edit.
6. Identifikasi source of truth dan ownership sebelum membuat state/mechanism baru.
7. Terapkan perubahan terkecil yang BENAR; jangan memperluas scope.
8. Pertahankan behavior unrelated dan compatibility yang relevan.
9. Validasi sesuai risiko terhadap code/SHA yang benar-benar diuji.
10. Review seluruh diff; jangan melemahkan test/evidence agar hijau.
11. Jangan mengklaim lebih dari evidence aktual.
12. Ikuti Working Guide untuk branch, PR, CI, release, concurrency repository, dan delivery.

Prinsip:
CORE RULES SUMMARIZE; DETAILED RULES GOVERN.

============================================================

Gunakan hierarki:
1. Instruksi task eksplisit terbaru dari owner.
2. Specification/governing document task-specific yang authoritative.
3. LALAPO_WORKING_GUIDE_UPDATED.txt untuk repository/branch/PR/CI/release/delivery.

5. Repository-specific authoritative docs yang relevan untuk behavior yang sudah dikontrak, termasuk:
   - docs/Lalapo_V2_UI_UX_Spec.md
   - docs/FORK_IDENTITY.md
   - .github/RELEASE.md
   Jika task-specific governing document menyatakan precedence berbeda, ikuti task tersebut.
6. soul.md sebagai default collaboration/reasoning/design profile.
7. Pola Kerja Lalapo.txt hanya bootstrap/entrypoint dan tidak mengoverride authority di atas.

Repository/source aktual tetap menjadi implementation source of truth untuk kondisi kode yang benar-benar ada.
Governing document/task authoritative menentukan intended behavior/policy.
Perbedaan keduanya harus diselesaikan dengan evidence, bukan ditebak.

Task owner menentukan:
APA yang harus dicapai.

AI Working Protocol menentukan:
BAGAIMANA masalah dianalisis dan kode diubah.

Working Guide menentukan:
BAGAIMANA perubahan divalidasi dan dikirim melalui repository/CI/release flow.

============================================================
2. PRINSIP ENGINEERING UTAMA
============================================================

Urutan prioritas:
1. Correctness
2. Mencegah regression
3. Root-cause resolution
4. Data/state integrity
5. Playback/source compatibility
6. Scope discipline
7. Backward compatibility
8. Maintainability
9. Security
10. Performance
11. Developer experience
12. Implementation speed

Tujuan bukan menghasilkan diff terkecil.
Tujuan adalah menghasilkan perubahan terkecil yang BENAR.

Jangan memilih patch kecil jika patch:
- hanya menyembunyikan gejala;
- menambah workaround baru;
- membuat duplicate source of truth;
- bergantung pada timing/arbitrary delay;
- menimbulkan race condition;
- membuat implementation lama dan baru berjalan bersamaan tanpa ownership jelas;
- mengorbankan playback/source/download/backup compatibility.

Jangan melakukan refactor besar jika perubahan lokal yang bersih sudah cukup.

============================================================
3. PAHAMI INTENT OWNER
============================================================

Bedakan:
A. Tujuan owner.
B. Dugaan owner mengenai root cause.
C. Solusi teknis yang diusulkan owner.

Tujuan owner adalah target utama.

Dugaan root cause dan proposed solution harus diverifikasi terhadap repository.

Jika proposed solution tidak aman:
- pertahankan tujuan owner;
- gunakan solusi yang lebih benar;
- jelaskan trade-off bila material.

============================================================
4. DEFAULT SCOPE POLICY
============================================================

Anggap setiap task mempunyai scope sempit kecuali owner meminta perubahan luas.

Default flow:
TASK
-> INVESTIGATION
-> ROOT CAUSE / DESIGN PATH
-> MINIMAL CORRECT CHANGE
-> ENGINEERING VALIDATION
-> DIFF REVIEW
-> DELIVERY SESUAI WORKING GUIDE

Jangan melakukan opportunistic cleanup.

Jika menemukan masalah lain:
- catat;
- nilai apakah menghalangi task;
- jika tidak menghalangi, jangan perbaiki;
- laporkan bila relevan.

Prinsip:
IF OUTSIDE SCOPE: REPORT, DO NOT FIX.

============================================================
5A. EXTERNAL PROVIDER/API EVIDENCE AUTHORITY
============================================================

Untuk source/extension, stream, tracker, OAuth, Google Drive, SDK, dan API eksternal,
repository Lalapo adalah bukti tentang integrasi saat ini, bukan otomatis kontrak

rate limit, attribution, dan compatibility material dengan dokumentasi resmi/current
atau actual response evidence bila tersedia.
Jangan mengarang field/endpoint/capability. Bila tidak cukup evidence, nyatakan
INFERENCE, HYPOTHESIS, atau UNKNOWN; jangan mempromosikannya menjadi PROVEN.
Jangan mengirim integration berisiko terhadap correctness, data, security,
atau compatibility berdasarkan contract yang belum terverifikasi.
Minta owner hanya jika required evidence yang tidak tersedia benar-benar
memblokir keputusan aman.

============================================================
6. ROOT CAUSE FIRST
============================================================

Anggap gejala bukan root cause sampai dibuktikan.

Contoh data/state path Lalapo dapat berbentuk:
Database / Preferences / Filesystem
-> Repository / Interactor
-> Flow
-> Presenter / ScreenModel / ViewModel
-> Compose/UI

Playback path dapat berbentuk:
Source/Extension
-> episode/stream resolution
-> headers/cookies/stream metadata
-> playback handoff
-> player session/mpv
-> progress/history persistence
-> Library/History/Continue Watching

Download path dapat berbentuk:
Download queue/worker
-> filesystem
-> persistence/cache
-> observer
-> UI/offline playback

Cari titik pertama di mana expected state berbeda dari actual state.
Perbaiki divergence sedekat mungkin dengan ownership sebenarnya.

- player/session state;

============================================================
25. PERFORMANCE
============================================================

Correctness lebih penting daripada micro-optimization.

Periksa bila relevan:
- repeated DB query;
- N+1;
- unnecessary full-list refresh;
- duplicate Flow collection;
- blocking main thread;
- expensive recomposition;
- large allocation;
- unbounded cache;
- repeated source/network request;
- unnecessary player reinitialization;
- repeated stream resolution;
- expensive image decoding;
- download/player contention.

Performance fix harus memiliki evidence yang sesuai jika klaim performa material dibuat.

============================================================
26. ERROR HANDLING
============================================================

Jangan menyembunyikan kegagalan agar flow terlihat berhasil.

Hindari:
- catch Exception { } tanpa handling;
- fake success;
- silent fallback yang menutupi corruption/error;
- retry tanpa batas;
- mengubah unavailable stream menjadi state seolah playback berhasil.

Pertahankan informasi diagnosis yang cukup tanpa mengekspos secret.

============================================================
27. SECURITY & SECRETS
============================================================

Jangan:
- hardcode secret;
- commit credential;
- commit signing key;
- commit OAuth client secret;
- log token/password;
- menampilkan repository secret dalam chat/log;
- melemahkan certificate/input validation tanpa requirement kuat;
- menjalankan untrusted code untuk sekadar memperoleh diagnosis.

Repository release menggunakan secret yang terdokumentasi di .github/RELEASE.md.
Secret adalah external requirement, bukan source content.

============================================================
28. BACKWARD COMPATIBILITY
============================================================

Jangan hanya memikirkan fresh install.

Pertimbangkan existing users dengan:
- database lama;
- library/history/progress lama;
- downloads lama;
- preferences lama;
- backup lama;
- cached state;
- OAuth callbacks;
- extension repositories/deep links;
- tracker sessions;
- partially completed operation.

Fresh install bekerja tidak membuktikan upgrade path aman.

============================================================
29. KNOWN-GOOD / REFERENCE VERSION
============================================================

- commit lama;
- branch/tag;
- PR;

============================================================
30. SCREENSHOT / VIDEO / LOG
============================================================

Untuk crash/log:

1. exception utama;
2. caused-by chain;
3. application stack frame;
4. thread;
5. lifecycle/runtime context;

Pisahkan:
ROOT CAUSE
dari

============================================================
31. TESTING STRATEGY
============================================================

Pilih validation berdasarkan risiko dan perubahan nyata.

Unit/regression test harus:
- membuktikan contract yang relevan;
- tidak terlalu terikat implementation detail;
- gagal untuk regression yang dimaksud;
- tidak hanya mengunci bug workaround.

Jangan menghapus/melemahkan test agar perubahan hijau.

CI/delivery gate aktual mengikuti Working Guide.

============================================================
31A. TEST INTEGRITY
============================================================

Jangan menghasilkan CI hijau dengan menghapus/skip test, melemahkan assertion,
mengubah expected value/fixture/golden/acceptance guard untuk menerima regression,
memperlebar tolerance tanpa justification, atau menambah retry yang menutupi failure.
Test/fixture boleh direvisi hanya jika requirement owner memang berubah,
test terbukti salah/stale, atau perubahan expected behavior disetujui dan
didukung evidence. Jelaskan alasan dalam review/diff.
FIX THE CAUSE; DO NOT WEAKEN THE EVIDENCE.

============================================================
32. DIFF REVIEW
============================================================

Sebelum delivery:
- review semua file berubah;
- pastikan setiap perubahan berkaitan dengan task;
- cari accidental rename/reformat;
- cari secret;
- cari compatibility regression;
- cari duplicate state/job/collector;
- cari perubahan behavior tak diminta;
- cari perubahan build/release identity tak disengaja;
- pastikan tests tidak dilemahkan.

============================================================
33. EVIDENCE LANGUAGE
============================================================

Gunakan bila membantu:
PROVEN — dibuktikan oleh source/test/runtime/log.
INFERENCE — kesimpulan kuat dari evidence.
HYPOTHESIS — dugaan yang perlu diuji.
UNKNOWN — evidence belum cukup.

Jangan menyamakan:
- static/source review;
- local/unit test;
- CI;
- emulator/runtime;
- physical-device test;
- production evidence.

============================================================
33A. INFORMATION GAIN & SUFFICIENT EVIDENCE
============================================================

Gunakan definisi PROVEN / INFERENCE / HYPOTHESIS / UNKNOWN di §33.
Untuk investigasi kompleks pilih single targeted experiment dengan information gain
tertinggi: reproduction, instrumentation, targeted test, known-good comparison,
bisect, atau small A/B. Jangan mengulang broad audit atau hipotesis yang terbantah.
Berhenti ketika evidence minimum cukup untuk root cause/design, owning layer,
scope, regression surface, diff, dan validation sesuai risiko.
Catat unknown non-blocking sebagai follow-up; jangan mengklaim device/production
proof dari static, compile, unit, CI, atau emulator proof.

============================================================
34. STOP CONDITIONS
============================================================

STOP dan minta keputusan owner bila:
- requirement produk benar-benar ambigu dan dua pilihan mengubah behavior;
- task memerlukan credential/secret yang tidak tersedia;
- perubahan compatibility besar memerlukan product decision;
- task memerlukan physical-device observation yang tidak dapat digantikan evidence lain;
- destructive/final action membutuhkan authorization menurut Working Guide;
- governing document conflict tidak dapat diselesaikan dari evidence.

Jangan STOP untuk pertanyaan yang dapat dijawab dari repository/tool.

============================================================
34A. AUDIT MODE
============================================================

AUDIT default adalah READ/MAP/INVESTIGATE, bukan mengubah semua temuan.
Pisahkan INVESTIGATION (root cause/ownership/legacy/concurrency/regression),
IMPLEMENTATION (hanya in-scope yang disetujui), dan VALIDATION (evidence
terhadap tested code/SHA). Kelompokkan P0 data loss/crash, P1 correctness,
P2 moderate issue, P3 cleanup. Out-of-scope: REPORT, DO NOT FIX.

============================================================
35. DEFINITION OF ENGINEERING DONE
============================================================

Engineering work dianggap siap dikirim bila:
- intent dipahami;
- root cause/design path dibuktikan secukupnya;
- source of truth/ownership jelas;
- perubahan scope-correct;
- compatibility relevant dipertahankan;
- validation sesuai risiko dijalankan;
- full diff direview;
- tidak ada klaim evidence berlebihan;
- delivery mengikuti LALAPO_WORKING_GUIDE_UPDATED.txt.

Prinsip akhir:
UNDERSTAND THE REAL SYSTEM, FIX THE REAL CAUSE, PRESERVE THE REAL CONTRACT.
